# Galen v1 严格对照实验协议

## 0. 这项实验要回答什么

我们不把问题写成“Galen 是否比所有通用 Agent 更聪明”。真正可检验的问题是：

> 在康复科研的数据治理、连续上下文、工具执行和证据交付任务上，Galen 的项目状态层、RehabID 数据契约、执行契约和证据链接，是否能在相同输入与相同运行时下，提高可交付结果的可靠性，并降低无效操作成本？

这一区分必须保留：同运行时实验用于归因；Codex、Claude Code、OpenCode 的原生产品实验用于回答“为什么不是直接用通用工具”。后者会受到模型、默认提示和产品权限的共同影响，只能称为系统级参考，不能冒充架构因果证据。

## 1. 问题定义与验收对象

### 1.1 目标用户任务

目标用户是进行运动疲劳与康复科研的研究者。一次任务的“完成”不是回答写得像，而是：

1. 当前研究范围和关键事实被正确保持；
2. 数据被规范化、清洗并保留时间与来源；
3. 必要工具按任务契约完成调用且不循环；
4. 结论可以回到可打开的证据或原始数据；
5. 要求的 Markdown、JSON、CSV、PDF 等产物真实存在、非空并可预览。

### 1.2 主要研究问题

| 编号 | 问题 | 对照方式 | 主要证据 |
|---|---|---|---|
| RQ1 | 项目状态层是否减少长上下文、修订和范围切换错误？ | `full_galen` vs `stateless` | PCTX01–05 |
| RQ2 | RehabID 数据契约是否提高质量问题识别和溯源完整性？ | `full_galen` vs `no_data_contract` | PDATA01–05 |
| RQ3 | 执行契约是否减少重复调用、越权调用和失败后失控？ | `full_galen` vs `no_exec_contract` | PTOOL01、03–05 |
| RQ4 | 证据链接层是否提高“搜到—引用—可验证”的闭环？ | `full_galen` vs `no_evidence_link` | PTOOL02、PDATA05 |
| RQ5 | 同一模型和工具下，完整 Galen 是否优于无专用编排的通用基线？ | `full_galen` vs `generic_same_runtime` | 全部 15 卡 |
| RQ6 | 面对成熟通用产品，为什么仍需要 Galen？ | 原生 Codex / Claude Code / OpenCode 参考轨 | 任务覆盖、硬门、成本、可追溯性 |

## 2. 系统与“Galen 之前”的基线

### 2.1 主实验轨（可归因）

主实验固定同一模型 ID、provider、温度、最大输出、工具 API、fixture、超时和预算，只开关 Galen 机制：

| 系统 ID | 定义 | 可以归因的差异 |
|---|---|---|
| `full_galen` | 状态层 + RehabID 数据契约 + 执行契约 + 证据链接 | 完整架构 |
| `stateless` | 关闭项目状态层 | 上下文连续性 |
| `no_data_contract` | 关闭 schema、质量状态和数据溯源 | 数据治理 |
| `no_exec_contract` | 关闭白名单、预算和恢复协议 | 工具执行 |
| `no_evidence_link` | 关闭结论到证据的可点击映射 | 可核验交付 |
| `generic_same_runtime` | 关闭上述专用编排，但保留同模型、同工具、同 fixture | “Galen 之前”的最公平软件基线 |

这里的 `generic_same_runtime` 是最重要的“之前”：它模拟把同一个模型和工具直接交给普通 Agent 使用，而不是把旧版本不受控的聊天记录当作实验基线。

### 2.2 产品参考轨（回答“为什么不用 Codex/Claude Code”）

每个产品使用其公开支持的非交互模式，在隔离工作区运行同一 15 张任务卡。禁止改写用户全局配置；通过临时工作区、只读/最小权限、独立输出目录和固定超时运行。若某产品无法提供同等工具或产物能力，记录为 `capability_gap`，不把缺失能力误判成模型失败。

| 参考系统 | 运行口径 | 结论边界 |
|---|---|---|
| `codex_native` | 独立 profile/临时工作区，非交互 JSON 事件，固定模型和权限 | 产品级参考，不用于架构因果归因 |
| `claude_code_native` | `-p` 非交互，固定 model、max turns、permission mode 和 allowed tools | 产品级参考，不用于架构因果归因 |
| `opencode_native` | 固定 provider/model、工具权限和工作区，记录版本 | 产品级参考，不用于架构因果归因 |

每个参考系统必须先跑一个 `adapter_check`：确认它能读 fixture、写入指定目录、返回结构化 trace，并能被同一评测器解析。不能通过 adapter check 的系统只报告覆盖缺口，不进入胜负排名。

## 3. 冻结的任务套件

任务套件为 `evals/cases/paired/` 的 15 张卡，每卡都有公开 prompt、脱敏 fixture、硬门、预算和 evaluator-only gold：

| 组 | 任务卡 | 检验内容 |
|---|---|---|
| PCTX | PCTX01–05 | 长上下文保持、修订、范围切换、干扰恢复、文件事实落地 |
| PDATA | PDATA01–05 | schema 规范、重复/缺失、时间对齐、冲突保留、溯源完整 |
| PTOOL | PTOOL01–05 | 读写、证据检索、跨文件合并、失败恢复、正式产物交付 |

冻结规则：正式运行前生成 `suite_manifest.json`，记录每张卡的 SHA-256、版本、fixture 哈希和评测器版本。运行中不得修改 prompt、gold、fixture 或阈值；如发现任务缺陷，整批作废并递增 suite 版本。

## 4. 主要指标与公式

### 4.1 主终点：硬门通过

对每一张卡的每一次运行定义：

\[
H = F \times S \times E \times B \times D
\]

其中：

- `F`：必需事实全部保留；
- `S`：禁止事实/旧范围零泄漏；
- `E`：要求的工具调用和参数满足契约；
- `B`：未超模型请求、工具调用、重复调用和时限预算；
- `D`：产物存在、非空、格式正确、可预览，证据链接可验证。

主报告同时给出 `H`、五次全通过率 `Pass^5`、Wilson 95% 区间和每个硬门分项，不能用综合分替代。

### 4.2 二级指标

| 维度 | 指标 | 计算 |
|---|---|---|
| 上下文 | 事实召回率 | retained required facts / required facts |
| 上下文 | 旧范围泄漏率 | 含 forbidden 命中 的运行数 / 总运行数 |
| 数据 | 数据问题识别率 | 正确识别的问题数 / fixture 中已知问题数 |
| 数据 | 溯源完整率 | 同时含 `rehab_id、timestamp、source、collection_context、quality_status` 的关键记录 / 关键记录总数 |
| 证据 | 检索可核验率 | 能打开且元数据一致的引用 / 要求引用 |
| 证据 | 引用覆盖率 | 已引用的必需证据 / 必需证据 |
| 交付 | 产物可预览率 | 可打开的非空产物 / 要求产物 |
| 成本 | 模型请求数 | 每卡触发的模型轮数 |
| 成本 | 工具调用数 | 每卡工具调用总数 |
| 成本 | 重复调用率 | 相同工具+相同输入的重复调用 / 工具调用 |
| 速度 | TTFR、总时延 | 首次可用响应、最终交付的毫秒数 |
| 稳定性 | 恢复成本 | 失败后额外模型请求、工具调用和等待时间 |

效率只有在 `F/S/E/B/D` 全部不退化时才解释。Token 少但事实丢失、链接失效或产物打不开，记为失败而不是收益。

## 5. 公平性与防止自嗨的规则

1. **同输入**：15 张任务卡逐字相同，fixture 和输出契约相同。
2. **同预算**：统一 timeout、max model requests、max tool calls、最大重复次数。
3. **同工具语义**：主实验使用同一工具 schema 和返回 fixture；外部产品使用 adapter，所有能力缺口单列。
4. **无 gold 泄漏**：`required.facts`、`required.artifacts` 和 forbidden patterns 只在 evaluator 侧，绝不注入模型可见 prompt。
5. **版本可追溯**：记录系统版本、模型 ID、provider、参数、机器、时间、suite hash、代码 commit 和完整 trace。
6. **不挑结果**：所有卡、所有重复都进入报告；失败、超时、provider 402 和 capability gap 分开计数。
7. **预注册停止条件**：单个 provider 出现全零请求或连续 402 时停止该批，标记 `provider_unavailable`，不补写、不回填、不进入排名。
8. **盲态分析**：统计脚本先读取系统 ID 的匿名别名；图表和论文在冻结统计后再揭示名称。
9. **重复与随机性**：冒烟 1 次只用于查链路；正式每卡每系统 20 次，至少 5 次才能发布阶段性结论。能固定 seed 则固定；不能固定则记录随机种子/采样设置。
10. **现实边界**：跨产品结果写成“在本任务套件和本运行配置下”；只有同运行时消融才能写“该架构机制带来增益”。

## 6. 统计分析计划

1. 以“任务卡 × 重复编号”为最小观察单位，按 PCTX、PDATA、PTOOL 分层。
2. 主比较为 `full_galen - generic_same_runtime` 的硬门通过率差；报告差值、Wilson 95% 区间和按任务卡聚类的 paired bootstrap 95% CI。
3. 二元配对结果补充 McNemar 检验；连续指标报告中位数、P50/P90 和配对 bootstrap 区间。
4. 只有当主终点不下降、所有发布硬门保持通过，且成本指标改善达到预注册阈值（工具调用或模型请求至少下降 15%）时，才称为“效率改善”。
5. 多个系统比较使用 Holm 校正；不把 GAI 或任意加权分数当作主结论。
6. 报告完整失败谱：事实遗漏、旧范围泄漏、工具越权/循环、证据失链、数据质量漏检、产物失败、超时、provider 不可用、能力缺口。

## 7. 为什么仍然需要 Galen

这不是“通用 Agent 不聪明”，而是目标函数不同：

| 需求 | 通用编码 Agent 的默认对象 | Galen 的专用对象 |
|---|---|---|
| 状态 | 会话/代码仓库上下文 | 研究项目、RehabID、时间轴和当前范围 |
| 数据 | 文件能否读写 | 单位、缺失、冲突、采集场景和质量状态 |
| 执行 | 尽快完成命令 | 工具白名单、预算、重试和失败可解释 |
| 证据 | 文字回答或代码 diff | 每个结论回到 PMID/DOI/URL/原始记录 |
| 交付 | 文件生成即可 | 可预览、可复核、可继续研究的正式产物 |

因此 Galen 的销售和商务叙事应是：

> 通用 Agent 负责通用推理与操作；Galen 负责把康复科研所需的状态、数据、证据和交付契约固定下来。我们不是重新训练一个更大的聊天模型，而是把“研究能否被连续、可核验地完成”变成可测量的系统能力。

路演只展示三件事：同一任务卡的前后结果、同一任务卡与通用产品的可复核差异、以及失败时 Galen 如何保留证据和状态。所有口号都必须能落到 `records.jsonl`、截图或可打开链接。

## 8. 执行阶段与发布门

### 阶段 A：协议冻结

- [x] 15 张任务卡、指标口径和 6 个主实验变体已在仓库；
- [ ] 生成 suite manifest 并锁定评测器 commit；
- [ ] 为三个外部产品完成 adapter check，不改用户全局配置。

### 阶段 B：内部正式实验

- 每卡 × 每变体 × 20 次；
- provider 正常且 manifest 为 `completed`；
- 先通过硬门，再做统计和图表。

### 阶段 C：产品参考实验

- Codex、Claude Code、OpenCode 各跑 adapter check 后再跑 5 次先导；
- 先导只用于定位能力缺口；稳定后再扩至 20 次；
- 结果分为“同运行时架构证据”和“原生产品参考”两张表。

### 阶段 D：论文与商务交付

- 论文：方法、任务卡、指标、完整失败谱、原始 trace 索引、统计脚本；
- 路演：一张问题定义图、一张任务矩阵、一张硬门对照图、一次完整演示；
- 商务：用同一套数字回答“为什么不是直接使用通用 Agent”，不声称普遍优于所有模型。

**发布门：** 未完成内部 20 次重复、外部产品至少通过 adapter check、或存在未解释的 provider/capability 缺口时，只能称为“评测准备完成”，不能称为“Galen 已被证明优越”。
