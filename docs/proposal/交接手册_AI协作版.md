# Galen Rehab Intelligence 计划书交接手册（AI 协作版）

更新日期：2026-09-03

## 1. 你接手的任务

在现有主计划书基础上完成参赛文本，不重新发明项目方向。主计划书的结构、产品关系、首个场景和核心叙事已经确定；接手者主要负责补全企业需求、市场、团队、商业化、实施计划及文字一致性，并与技术佐证报告交叉核验。

## 2. 已冻结的核心叙事

项目名称：**Galen Rehab Intelligence：面向运动疲劳恢复的多模态连续评估与康复辅助系统**。

以下内容不得擅自改变：

1. 首个验证场景是**运动疲劳恢复**，不是泛化到所有疾病的通用康复平台。
2. 长期愿景是**康复对象的连续多模态状态系统**。
3. 系统监测的是“人”，设备、量表和软件只是不同的感知与交互入口。
4. 核心闭环是：**工作台采集 → Rehab ID 汇聚 → Galen 分析 → Recovery Companion 回流 → 专业人员再决策**。
5. `ATH-001` 是标准化演示病例；真实人体实验结果必须在 Pilot 阶段单独采集、复核和报告。
6. 当前不把自研硬件写成已完成产品。硬件路线是：先接入现有设备，发现关键数据缺口后再设计专用传感硬件。

## 3. 三个软件的准确关系

### 康复师工作台

专业端与真实世界数据入口，负责接诊、评估、报告和记录。当前计划书使用 `ATH-001` 展示 Rehab ID、四项评估和恢复期报告。

### Galen

智能分析与证据中枢，负责纵向状态分析、模型比较、误差解释、证据对齐和研究产物生成。它不是单纯聊天机器人。

### Recovery Companion

用户/运动员侧的离场随访入口。现有产品已具备训练任务与每日反馈能力；竞赛版本需要收束为睡眠、RPE、疼痛、训练完成度和主观恢复，并回流到同一 Rehab ID。

三者是同一系统的三个界面，不要写成三个彼此无关的软件，也不要让家长端或青跃工作台取代主产品。

## 5. 下一位 AI 的工作顺序

1. 完整阅读主计划书 PDF 和本手册。
2. 对照命题文件补齐企业痛点、命题匹配、应用价值和合作方式。
3. 补齐团队成员、职责、已有成果、知识产权与资源条件；没有材料的字段必须向项目负责人索取，不得编造。
4. 完善商业模式、实施进度、风险与验收指标，但不得冲淡运动疲劳恢复主线。
5. 完善技术佐证报告，将每一项“已实现”绑定到代码仓库、版本、截图、测试或运行产物。
6. 最后统一检查计划书、技术佐证、PPT 和演示脚本是否使用同一套术语和数字。

## 6. 技术佐证必须补齐的内容

- 三端系统架构和职责边界。
- Rehab ID 数据结构及基线、疲劳后、恢复期三个时间点的字段样例。
- HRV、CMJ、RPE、VAS、睡眠和训练负荷的来源、单位、时间戳、采集条件与质量状态。
- 工作台、Galen、Recovery Companion 的仓库地址、分支、版本与构建方式。
- 自动化测试、构建日志、真实运行截图和演示数据说明。
- Pilot 的受试者、疲劳任务、时间点、指标、专业复核和统计分析方案。
- 演示数据与真实实验数据的明确边界。

## 7. 禁止事项

- 不把项目写成“万能医疗 AI”或“覆盖所有康复场景”。
- 不把 Galen 写成普通科研聊天助手。
- 不把青跃工作台写成当前主工作台。
- 不把小柱家长端的儿童脊柱场景写成比赛主线。
- 不把演示数据包装成真实实验结果。
- 不堆砌大模型、RAG、多 Agent、知识图谱等名词而不说明其具体任务。
- 不在没有现成证据时宣称诊断准确率、临床效果或商业收入。

## 8. 写作验收标准

完成稿必须让评委在三分钟内回答四个问题：

1. 解决谁的什么问题？
2. 三个软件如何围绕同一个 Rehab ID 协作？
3. 当前已经做出了什么，哪些仍属于 Pilot？
4. 科大讯飞等企业为什么需要这一康复场景数据与应用层？

如果任何章节不能服务这四个问题，应删减或改写。
