# Galen Rehab Intelligence 技术佐证报告 v1

## 摘要

本报告说明 Galen Rehab Intelligence 已形成的软件工程、状态数据组织和自动化评测基础。系统以运动疲劳恢复为首个验证场景：将同一受试者的基线、疲劳后与恢复期记录纳入统一 Rehab ID，进而生成连续状态画像、来源追溯和专业工作流产物。

当前工程已具备 Galen 桌面端、文献检索与可点击引用、研究任务和交付物预览、康复师工作台、用户侧随访代码基础及可复现评测合同。真实疲劳 Pilot、工作台与 Recovery Companion 的最小数据回流，是本报告定义的下一阶段验证任务。

## 2. 工程总体结构

```text
康复师工作台
  受试者 / 评估 / 报告 / 随访
          ↓
Rehab ID + 统一数据协议
          ↓
Galen 状态与证据引擎
  时间轴 / 变化检测 / 依据链接 / 报告产物
          ↑
Galen Recovery Companion
  睡眠 / RPE / 疼痛 / 训练完成度 / 主观恢复
```

系统的中心对象是受试者状态，而非某一种设备。工作台负责专业数据和工作流，Galen 负责持续状态组织、解释和证据，Recovery Companion 负责离场后的轻量恢复随访与数据回流。

## 3. Rehab State Schema v0.1

| 一级维度 | 代表数据 | 典型来源 | 在运动疲劳场景的作用 |
|---|---|---|---|
| 生理恢复 | HRV、心率、睡眠、血乳酸 | 可穿戴、检验记录 | 描述自主神经与生理恢复线索 |
| 功能能力 | CMJ、力台、动作、ROM、肌力 | 力台、视觉、评估 | 描述神经肌肉表现与功能变化 |
| 症状与风险 | 疼痛、疲劳、异常事件 | VAS、问卷、记录 | 标注限制因素与待确认变化 |
| 活动与参与 | 训练完成度、返训进度 | 教练记录、用户上报 | 描述状态在真实训练中的表现 |
| 心理与行为准备度 | RPE、主观恢复、依从性 | Companion、量表 | 描述主观负荷与恢复意愿 |
| 干预与环境 | 训练负荷、治疗、家庭训练 | 工作台、训练日志 | 为状态变化提供上下文 |

每条记录均保留横切元数据：`rehab_id`、时间点、指标名称、数值、单位、来源、采集条件、质量状态、干预上下文和证据链接。

## 4. 数据协议与接入方法

```json
{
  "rehab_id": "ATH-001",
  "timestamp": "2026-09-01T10:30:00+08:00",
  "state_dimension": "physiological_recovery",
  "metric_name": "HRV_RMSSD",
  "value": 41.2,
  "unit": "ms",
  "source_type": "wearable",
  "collection_context": "post_fatigue",
  "quality_status": "verified"
}
```

当前接入策略是开放式的：设备或量表可经 CSV、JSON、图片、表格或 API 进入标准化记录。接入后，系统不只保存数值，还保存它的来源和采集语境，确保后续变化解释可回查。

## 5. 连续状态计算与解释

系统采用三层逻辑：

```text
个人稳定期基线
→ 疲劳后相对变化
→ 恢复期相对变化
→ 生理、功能、症状、行为和训练上下文联合解释
→ 恢复阶段、驱动指标、信息缺口和依据链接
```

基础变化指标可写为：

```text
相对变化 = （当前值 - 个人基线） / 个人基线
```

不同指标保留方向性：动作表现和 HRV 的变化与 RPE、疼痛的变化不能以同一方向解释。系统输出应明确显示哪些变化驱动结论，而不是只给出一个不可拆解的“疲劳分数”。

## 6. Galen 已实现的证据与交付能力

Galen 当前版本的工程能力包括：

- 文献检索与来源覆盖状态；
- 关键建议后的可点击链接；
- 任务、决策、证据和产物的工作区状态；
- Markdown/PDF 等交付物预览；
- 长任务进度和证据链显示；
- 对信息缺口、来源不充分和工具执行结果的结构化呈现。

### M03 评测任务

`M03` 是腰痛功能受限的教学推理任务，用于验证“输入信息缺口不能被模型补写成事实”的工程约束。任务要求系统生成带依据链接的交付物，并对最终产物扫描禁止模式。

实测中，系统曾把未提供的性别写成“男性”。随后评测器增加 `artifact_patterns` 硬门：若交付物出现本病例未给出的性别断言，任务立即失败。修复后一次真实执行通过：`pass=true`、质量分 `1.00`、总耗时约 27 秒。

该任务证明的是 Galen 的可追溯交付与防编造工程能力，不代表运动疲劳 Pilot 的临床验证。

## 7. 康复师工作台与 Recovery Companion

康复师工作台已形成接诊、评估、报告与数据中心的专业工作流基础。企业赛 Demo 不应截取空状态页，而要先用 `ATH-001` 等去标识化演示记录填充：基线、疲劳后、恢复后，包含 HRV、CMJ/力台、RPE、VAS、睡眠和训练负荷。

Recovery Companion 不以独立聊天助手身份展示，而是作为运动员侧的“最后一公里”随访：每日或训练后收集睡眠、RPE、疼痛、训练完成度和主观恢复，并将这些记录回流至同一 Rehab ID。

## 9. 运动疲劳 Pilot 验证方案

### 研究问题

多模态连续记录是否比单独查看 HRV、CMJ/力台或 RPE，更完整地支持专业人员判断运动疲劳后的恢复阶段？

### 采集设计

```text
受试者招募
→ 基线采集
→ 标准化疲劳任务
→ 疲劳后复测
→ 恢复期复测
→ Galen 状态画像
→ 治疗师/教练复核
```

### 采集指标

HRV、CMJ/力台、动作表现、RPE、VAS、睡眠、训练负荷；如实验条件具备，可加入血乳酸和其他生理指标。

### 评价指标

- 时间点、来源、单位和采集条件的数据完整率；
- 状态变化识别覆盖度；
- 关键解释的来源与时间点追溯率；
- 与专业人员恢复判断的一致性；
- 与单指标判断相比增加的有效信息；
- 生成一次恢复回顾与报告的时间。

## 10. 产品演进与硬件接口

```text
接入现有设备
→ 建立统一 Rehab ID 与数据协议
→ 从连续记录中发现关键数据缺口
→ 针对缺口设计专用智能传感硬件
→ 形成软硬件闭环
```

当前主交付是软件与数据层。未来硬件的价值不在于“多一个设备”，而在于补上连续状态系统已经识别出的关键感知缺口，例如家庭训练质量、动作负荷或恢复依从性。
