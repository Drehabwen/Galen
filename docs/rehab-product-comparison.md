# AI 康复产品线比较

来源目录：`D:\Users\DORAT\Desktop\03_AI康复项目`  
日期：2026-07-07  
用途：比较历史产品资产，判断哪些应继续作为主线、模块、迁移来源或归档资产。

## 1. 总体判断

这个目录不是单一项目，而是一个 AI 康复产品组合。当前资产大致形成过一条三端闭环：

```text
早筛端 -> 康复师工作站 -> 家长/患儿端
```

对应产品：

- `早筛/`：现场轻量筛查端，原 SquatLab 方向。
- `Rehab-main/`：B 端康复师工作站，也是当前集成中枢。
- `chatbotagent/` 与 `RehabGPT-feat-biz/`：C 端家长/患儿助手，小柱。

另有一个重要重写候选：

- `青跃康复工作台/`：更干净的新工作台主线，但目前不是三端闭环的现有中枢。

结论：

- 如果目标是继续做 AI 康复闭环，`早筛 + 青跃康复工作台 + 小柱` 是更合理的未来产品形态。
- `Rehab-main` 应作为当前可运行的集成中枢和业务资产来源，不建议长期作为新产品外壳继续堆功能。
- `青跃康复工作台` 的身份契约、intake 队列、家庭访问、报告就绪模型，是最值得继承的产品架构。
- `早筛` 是最清晰的端侧产品，有实际 APK、明确筛查场景和同步闭环。
- `chatbotagent/小柱` 是家庭端闭环必要补位，但不能成为事实数据源。
- `POSE`、`Deeprehab-MedVoice-AI--`、`Rehab-Hub/Debt`、`openrehab/rehabclaw` 更适合作为模块、原型或历史参考。

## 3. 分项比较

### 3.1 Rehab-main

定位：

- B 端康复师工作站。
- 当前三端闭环的集成中枢。

已有能力：

- Vision3 体态分析。
- ROM 关节活动度评估。
- MedVoice 语音接诊与结构化病历。
- 量表评估。
- 报告中心、数据中心、前后对比。
- 治疗计划生成。
- 早筛同步导入。
- 家庭码、量表推送、结果回收。

优势：

- 功能最完整。
- 接口闭环最接近实际产品。
- 文档和测试资产较多。
- 已经承接 `早筛 -> B 端 -> 家庭端` 的真实集成路径。

问题：

- 历史功能堆叠明显。
- 多个模块同时承担集成、报告、状态、LLM 输出，容易形成巨石组件。
- 技术债文档显示曾有多个真相源、报告摘要质量、报告中心体量过大等问题。
- 适合作为业务事实来源，不适合作为未来新壳继续堆。

判断：

`Rehab-main` 是当前最有价值的运行资产，但未来应逐步让位给更干净的 `青跃康复工作台` 架构。

### 3.2 早筛 / SquatLab

定位：

- 轻量现场筛查端。
- 原 SquatLab 深蹲评估方向扩展为青少年体态和脊柱侧弯早筛。

已有能力：

- 深蹲动作筛查。
- Adams 前屈筛查。
- 跨协议姿势对称度评估。
- 受试者、筛查会话、综合报告。
- 同步到 Rehab-main 集成后端。
- Capacitor Android APK。

优势：

- 场景非常清晰：学校、社区、现场筛查。
- 产品边界清楚，不承担完整康复管理。
- 有 APK 和软著材料，交付感强。
- 和 B 端同步闭环已经被文档明确。

问题：

- 容易从轻量筛查膨胀成完整康复平台。
- 原 PRD 中 SquatLab 初始定位偏个人训练和深蹲评估，后续又加入早筛和 Adams，需要统一命名和产品叙事。
- 不能承接患者长期管理和家庭任务回流。

判断：

`早筛` 应保留为独立端侧产品，专注采集、筛查、初步报告、同步。不要把康复师工作站能力塞回早筛端。

### 3.3 chatbotagent / 小柱

定位：

- C 端家长/患儿助手。
- 康复师指令的承接层，连接诊室内外。

已有能力：

- 家庭码登录。
- 报告查看。
- 训练处方查看。
- 每日打卡。
- 量表填写。
- LLM 流式对话。
- 上下文引擎。

优势：

- 补齐家庭执行闭环。
- 产品叙事清楚：康复师做判断，家长做执行。
- 和 Rehab-main 的集成边界明确：Python 是唯一数据源，Node 只负责 LLM 流式对话。

问题：

- 容易变成普通聊天助手。
- 安全边界必须清楚，不能让家长端生成未经康复师确认的处方。
- 依赖 B 端数据质量，不能独立成立为主平台。

判断：

`小柱` 是闭环必要端，但应定位为家庭执行与反馈入口，不作为主数据源、不做主诊断、不主导处方生成。

### 3.4 青跃康复工作台

定位：

- 新版康复工作台或正式重写候选。
- 面向青少年体态和脊柱筛查后的康复管理。

核心设计：

- 早筛数据先进入待确认 intake。
- `patient_id` 是唯一业务主身份。
- `family_code` 是可撤销、可过期、只存 hash 的访问凭证。
- 报告中心读取明确的 `ReportReadiness`，不靠 tags 猜状态。
- 插件通过统一 SDK 交换数据，不直接操作全局 store。

优势：

- 架构文档最干净。
- 明确吸取了旧项目技术债。
- 身份、证据、报告就绪、家庭回流的契约成熟。
- 很适合作为未来正式产品主线。

问题：

- 当前实现体量小于 Rehab-main。
- README 仍是 Vite 模板，说明产品说明尚未完全落地。
- 还没有拥有 Rehab-main 的 `/api/integration/*` 闭环事实。
- 若直接替换 Rehab-main，需要迁移大量能力。

判断：

`青跃康复工作台` 是最适合作为“未来 B 端主线”的产品，但需要从 Rehab-main 迁移闭环 API、报告中心、评估插件和家庭端连接。

### 3.5 POSE

定位：

- AI 体态评估移动应用。
- 更偏通用用户、健身人群和个人体态改善。

优势：

- 产品目标简单。
- 移动端拍摄、姿势检测、LLM 建议的路径清晰。
- 可作为早筛端早期灵感来源。

问题：

- 医学闭环弱。
- 和当前青少年脊柱/康复师工作站方向相比，定位偏泛健康。
- 不是当前最有价值主线。

判断：

`POSE` 可归为早期体态评估原型，保留算法和移动交互参考即可。

### 3.6 MedVoice

定位：

- 语音转病例助手。

优势：

- 语音接诊和结构化病历能力非常适合嵌入 B 端工作站。
- Word 导出和本地病例结构化对报告/病历工作流有价值。

问题：

- 独立 tkinter 工具形态偏旧。
- 不应成为单独主产品。
- 需要统一到 Rehab/青跃的会话、患者、报告数据模型中。

判断：

MedVoice 应作为 `语音采集/结构化病历模块`，嵌入 B 端，而不是独立主线。

## 4. 与 Galen 的关系

Galen 当前定位是：

> 面向医学研究者的 AI 科研协作工作站。

康复产品线定位是：

> 面向康复筛查、评估、报告、处方、家庭执行和随访回流的临床服务闭环。

两者不要直接合并。它们共享底层思想，但产品对象不同：

| 维度 | Galen | 康复产品线 |
| --- | --- | --- |
| 核心对象 | 课题、文档、证据、代码、产物 | 患者、筛查、评估、报告、处方、随访 |
| 用户 | 医生/医学研究者 | 康复师、筛查人员、家长/患儿 |
| 主界面 | 科研执行线程 + 文档画布 | 工作台 + 评估流程 + 报告中心 |
| AI 角色 | 科研执行与修订 | 评估辅助、报告生成、处方解释 |
| 签核 | 研究者确认 | 康复师确认 |
| 证据 | 文献、数据、代码、版本 | 采集证据、评估指标、报告就绪、随访反馈 |

可复用思想：

- Galen 的 `科研执行线程` 可以启发康复端的 `评估执行线程`。
- Galen 的标签工作流可以用于康复端的风险、证据、待签核、复查状态。
- 康复端的 `ReportReadiness` 可以反哺 Galen 的文档/证据就绪模型。
- 康复端的三端闭环可以提醒 Galen 后续如果做临床研究协作，也需要明确身份、权限、签核和版本。

不建议复用：

- 不把患者管理和家庭处方塞进 Galen。
- 不把 Galen 的科研文档系统塞进早筛端。
- 不把康复端的运动处方硬件闭环并入当前 Galen 主线。

## 5. 推荐收敛路线

### 5.1 AI 康复产品线

建议未来产品结构：

```text
青跃智衡早筛端
  -> 青跃康复工作台
    -> 小柱家庭端
```

职责：

- `早筛端`：采集、筛查、初步报告、同步。
- `青跃康复工作台`：患者确认、评估证据、报告就绪、处方、随访、家庭任务。
- `小柱家庭端`：查看报告、执行任务、量表回填、训练打卡、对话解释。

迁移策略：

1. 保留 Rehab-main 作为当前运行中枢。
2. 以青跃康复工作台为未来 B 端壳。
3. 从 Rehab-main 迁移 integration API、报告中心、治疗计划和插件能力。
4. 早筛端保持独立，只对接工作台 intake。
5. 小柱端只消费工作台授权数据，不拥有事实数据源。

### 5.2 Galen 产品线

Galen 保持医学科研工作站定位：

```text
科研执行线程 -> 文档选区修订 -> 标签协作 -> 代码执行 -> 证据链 -> 研究者签核
```

Galen 可借鉴康复产品线的：

- 多阶段状态模型。
- 证据就绪模型。
- 签核机制。
- 标签驱动协作。
- 本地优先、后续同步的架构策略。

但 Galen 不应继承康复端的患者/家庭/处方工作流。

## 6. 最终排序

按“继续投入价值”排序：

1. `青跃康复工作台`：未来正式 B 端主线，架构最值得发展。
2. `早筛`：端侧筛查产品，边界清楚且可交付。
3. `Rehab-main`：现有集成事实源，迁移来源。
4. `chatbotagent/小柱`：家庭端闭环必需。
5. `MedVoice`：模块化嵌入能力。
6. `POSE`：早期移动体态评估原型。
7. `Rehab-Hub/Rehab-Debt`：历史分支，归档或比对。
8. `openrehab/rehabclaw`：技术实验资产。

一句话结论：

> 康复线应收敛为“青跃早筛端 + 青跃康复工作台 + 小柱家庭端”；Rehab-main 作为现有事实源和迁移资产；Galen 则保持医学科研协作工作站，不与康复服务闭环混线。
