# Galen 评测与负优化判定规范

状态：初始基线
适用范围：Prompt、上下文工程、模型参数、工具选择、Agent Loop、Session、Artifact 与 UI 恢复链路

## 1. 目的

Galen 的任何“优化”必须能够在固定任务、固定输入、固定模型配置下与基线比较。禁止仅凭单次运行体感、单一速度指标或个别成功案例判断优化成立。

本规范解决三个问题：

1. 如何建立可重复的 Galen 评测任务集。
2. 如何同时衡量科研质量、可靠性、速度、成本与用户干预。
3. 如何自动判定正优化、无显著变化和负优化。

## 2. 负优化定义

候选版本在相同任务、模型、数据和运行条件下，虽然改善了一个局部指标，但导致关键质量门失败，或者其收益不足以补偿其他指标的显著退化，即判定为负优化。

### 2.1 无条件负优化

出现以下任一情况，无论速度或 Token 改善多少，候选版本均不得接受：

- 研究结论与输入数据或证据冲突。
- 引用、Evidence 或 Artifact 无法追溯到真实来源。
- 统计方法与研究设计不匹配，或关键计算不可复现。
- 上下文压缩导致任务约束、关键决策或已接受证据丢失。
- 重启或恢复后重复执行已完成节点。
- 工作区之间发生会话、文件或任务状态串扰。
- 必需 Artifact 缺失、为空、无法打开或内部预览失败。
- 风险操作绕过权限或人工签核边界。

### 2.2 相对负优化

没有触发硬质量门，但满足以下任一条件时判为负优化：

- 综合研究质量相对基线下降超过 3 个百分点。
- P90 首次有效响应时间或任务总耗时恶化超过 10%，且质量提升不足 5 个百分点。
- 总 Token 或模型请求次数增加超过 15%，且质量、可靠性或耗时没有显著改善。
- 工具错误率、重复调用次数、人工干预次数或恢复失败率增加。
- 指标没有显著改善，但引入了新的持久状态、分支逻辑或故障点。

## 3. 优化接受规则

候选版本只有同时满足以下条件才可以替换基线：

1. 所有硬质量门通过。
2. 综合研究质量下降不超过 3 个百分点。
3. 至少一个主目标获得有意义改善：
   - TTFR P50 降低至少 15%；或
   - 完整任务耗时 P50 降低至少 15%；或
   - 总 Token 降低至少 15%；或
   - 任务成功率提高至少 5 个百分点；或
   - 人工干预次数降低至少 20%。
4. P90 延迟不得恶化超过 10%。
5. 工具错误率、循环率和恢复失败率不得增加。

初始阈值应在积累 20～30 组有效基线后，根据自然波动重新校准。阈值调整本身必须留下版本记录，不得为使某个候选版本通过而临时修改。

## 4. 分层测试体系

### 4.1 L0：确定性单元测试

不调用真实模型，验证：

- 稳定 System Prompt 不包含易变工作区或环境状态。
- 每轮 Context Assembler 能读取最新 ResearchTask、Evidence 和 `GALEN.md`。
- Session 追加、恢复、归档和工作区隔离。
- 压缩保留最近消息、任务锚点和工具调用/结果边界。
- 节点恢复完成前不会再次自动执行。
- 路径穿越、过期 revision 和重复 Evidence 被拒绝。

L0 在每次提交运行，任何失败都阻止合并。

### 4.2 L1：确定性组件与协议测试

使用固定模型桩和固定工具结果，验证完整请求结构：

- 模型可见的 System、Tools、Messages 与动态上下文。
- 首轮协议只出现一次，科研状态每轮刷新。
- 工具错误升级、停止条件和最大轮次收敛。
- Token、缓存和 TurnRecord 计量。
- Session 重放得到与原运行一致的模型可见上下文。

### 4.3 L2：真实模型固定任务集

首批黄金任务至少包含：

| ID | 场景 | 核心验收 |
| --- | --- | --- |
| E01 | 简单科研问答 | 快速产生正文，不调用无关工具 |
| E02 | PubMed 文献检索 | 文献真实、引用可验证、证据分级合理 |
| E03 | 本地 CSV/肌电分析 | 数据读取正确、方法合理、结果可复现 |
| E04 | 多节点科研计划 | 依赖正确、任务能够收敛、无无效循环 |
| E05 | 节点执行与回流 | ResearchTask 与 Evidence 正确更新 |
| E06 | 关闭应用后恢复 | 消息不丢失，已完成节点不重复执行 |
| E07 | 长上下文压缩 | 关键约束、结论和来源不丢失 |
| E08 | 工具失败恢复 | 能改变策略并在无进展时停止消耗 |
| E09 | Artifact 交付 | 产物存在、非空、可在 Galen 内预览 |
| E10 | 跨工作区隔离 | Session、Task、Evidence 与文件无串扰 |

每个案例必须定义输入工作区、用户任务、必需 Evidence、必需 Artifact、禁止行为、最大工具调用、最大人工干预和评分规则。验收比较事实、产物和状态变化，不比较模型逐字输出。

## 5. 指标

### 5.1 科研质量

- 任务成功率。
- 必需声明 Evidence 覆盖率。
- 引用真实性与可追溯率。
- 方法与研究问题匹配度。
- 结论是否超出证据。
- Artifact 有效性、内部预览率与可复现率。

### 5.2 可靠性

- 工具错误率。
- 同一工具和参数重复次数。
- 无新增 Evidence 的连续循环数 `stale_count`。
- 恢复失败率与重复执行率。
- 每项任务人工中断次数。

### 5.3 性能与成本

- 本地上下文组装耗时。
- MCP 准备耗时。
- 网络连接耗时。
- TTFT：首个模型 Token。
- TTFR：首个有意义正文或工具动作。
- 完整任务耗时。
- 模型请求与工具调用次数。
- 输入、输出、Cache Read、Cache Create Token。
- 上下文压缩次数与压缩耗时。

所有延迟至少报告 P50 与 P90，禁止仅报告平均值。

## 6. 对照实验协议

1. 固定模型 ID、模型配置、thinking level、工具集合和输入工作区快照。
2. 基线版本与候选版本使用同一案例定义。
3. 真实模型案例每个版本至少运行 5 次。
4. 采用 A-B-B-A 或随机交错顺序，降低网络时段偏差。
5. 每次运行生成不可变 JSONL 记录，包含 commit、配置摘要、指标和断言结果。
6. 比较器先执行硬质量门，再执行非劣效判断，最后判断性能收益。
7. 失败案例必须保留原始 RunLedger、Session、Evidence 与 Artifact 定位。

## 7. 建议目录

```text
evals/
├── cases/
│   ├── e01_quick_answer.toml
│   ├── e02_literature.toml
│   └── ...
├── fixtures/
├── baselines/
│   └── deepseek-v4-pro.json
├── runs/
│   └── <run-id>.jsonl
└── reports/
    └── <baseline>--<candidate>.html
```

运行记录至少包含：

```json
{
  "case_id": "E03",
  "commit": "<git-sha>",
  "model": "deepseek-v4-pro",
  "run_index": 1,
  "quality": { "score": 0.94, "hard_gates_passed": true },
  "latency": { "ttfr_ms": 4200, "total_ms": 38000 },
  "usage": { "input": 12000, "output": 1800, "cache_read": 9000 },
  "tools": { "calls": 5, "errors": 0, "max_repeat": 1 },
  "recovery": { "restored": true, "duplicate_execution": false },
  "artifacts": { "required": 2, "valid": 2, "previewed": 2 }
}
```

## 8. 基线治理

- `galen-research-workbench` 上最后一个通过全部硬质量门的版本才可以成为基线。
- 基线更新必须附带对比报告，说明接受理由和已知退化。
- 模型供应商升级模型 ID 时建立新基线，不与旧模型结果直接混合。
- 网络故障、供应商限流和测试数据损坏的运行标记为无效样本，不得选择性删除正常失败样本。
- 连续两次评测无法证明收益的复杂优化应撤销或缩小范围。

## 9. 当前实现差距

现有 `driver` 已能检查运行结束、工具错误、重复调用和产物存在，但还需要补齐：

- TOML 案例加载与工作区夹具重置。
- TTFT/TTFR 分段计时。
- 基线与候选批量运行。
- Evidence、Artifact 与恢复质量断言。
- P50/P90 聚合与非劣效比较器。
- HTML/JSON 对比报告。

在这些能力完成前，Prompt、上下文裁剪和模型参数调整只能作为实验候选，不得直接宣称为已验证优化。
