## 1. 一句话定位

DSH 是一个 **"一切皆插件"** 的 agent harness:连模型适配器、工具注册表、会话日志、甚至 agent 主循环本身都是插件,任何部件都可通过配置替换。底层运行时是 vendored 的 **Cordis**(`vendor/cordis/`),一个插件框架:插件贡献服务、类型化事件与**可逆 effect** 到共享 Context 上。

没有"特权内核"需要打补丁——扩展 DSH 的方式就是在旁边挂一个插件,注册项是 effect,插件卸载时自动回滚。

## 2. Cordis 五要素(底层框架)

| 概念 | 含义 |
|---|---|
| **插件** | 实现 Service 的对象:函数 + `inject` + `apply(ctx)`,或 Service 子类;Cordis 把其生命周期挂进当前上下文 |
| **上下文(Context)** | 服务的仓库;服务认领稳定的 `ctx.<key>`(如 `ctx.tools`),其他插件按 key 查找,不 import 具体实现 |
| **inject 依赖声明** | 声明所需服务,等服务存在才加载——加载顺序由服务依赖表达,而非手工排 boot 序 |
| **类型化事件** | 通过 TS declaration merging 声明事件名,按 `emit / waterfall / parallel / serial` 分发 |
| **可逆 effect** | 提示词分区、工具 schema、适配器、监听器都经 `ctx.effect()`/`ctx.on()` 安装,重载/卸载时按序回滚 |

**分发模式**(事件契约的一部分,`@mode` 标注):

| 模式 | 等待? | 顺序 | 返回值 |
|---|---|---|---|
| `emit` | 否 | 注册序观察 | 无 |
| `waterfall` | 否 | 注册序观察 | 有 |
| `parallel` | 是 | 并行 | 无 |
| `serial` | 是 | 注册序 | 有 |

**waterfall 语义**:围绕式中间件。监听器收 `(...args, next)`,调 `next()` 委派(可包装结果),不调 `next()` 即短路。策略类监听器(如守卫)常以"不调用 next 即拥有决策权"实现。

## 3. 组成:Profile / Bundle / Patch

一个运行的 DSH 是**启动时按序叠加出来的插件树**:

- **Profile**:Harness home 里一个命名组合(`$DSH_HOME/profiles/<name>/`),列出它叠加的 bundles,持有用户自己的 `cordis.patch.yml`。`web` 与 `headless` 是内置模板。
- **Bundle**:Cordis 配置行 + 代码的分发格式,在自身 `package.json` 的 `dsh.bundle.patch` 字段声明补丁文件。
- **Patch**:按 id 定位配置行,整体替换该行 config,或插入新行。层级顺序:profile 列出的各 bundle → profile 的 patch → home 级 patch → `--patch` 覆盖层。

三个出厂 bundle:
- `dsh-base`:每个 profile 的第一层——模型适配器、工具、持久化、沙箱+审批策略、设置、凭据、遥测。
- `dsh-web-app`:浏览器应用。
- `dsh-headless`:无服务器的一次性 runner。

`dsh --profile web --dump-config` 可打印本机实际 boot 的树,任何一行都能被用户 patch 覆盖。

## 5. 核心不变量:模型可见即已记录

这是 DSH 最深刻的设计原则:任何到达模型请求的内容,都必须能从会话日志重建。具体机制:

1. `SessionEvent` 是追加式、lossless-JSON、深冻结、seq 连续的日志,是唯一事实源。
2. 模型历史由 `deriveMessages()` 从日志投影(**surface 机制**,带缓存)。
3. `request/header` 事件记录完整请求头(config+system+tools),使每个请求成为日志的纯函数。
4. 运行时 invariant 断言"模型可见 ⇒ 已记录"。

推论:想给模型加一种新输入(如注入的上下文、goal 续跑轮),就必须**新增一种 session 事件类型**,并从日志渲染——没有旁路。

## 6. Turn / Step 生命周期(一次模型交互)

- **step** = 一次模型请求 + 它调用的工具; **turn** = 零或多个 step。
- 流程:`turn/start` → 认领 inbox 输入 → 组装提示词+工具 schema → `agent/pre-step`(可拒/改写)→ `step/start` → 落 `user/message` → `agent/request`(可换模型)→ `llm/stream`(chunk 全落日志)→ 组装 `assistant/message` → 工具经 `tools/pre-execute → execute → post-execute` → 有工具调用则下一 step → `turn/end`。
- `turn/*`、`step/*`、`user/message`、`assistant/*`、`tool/*` 是**耐久** session 事件;`agent/pre-step`、`agent/request`、`llm/stream`、`tools/*` 是**live** 扩展点(瀑布)。
- 失败结构化:`LlmError` 保留事实,未知错误扁平化为 `errorChain` 文本 + `UNKNOWN` 码;工具失败不断 turn。

## 7. 能力缝(Capability Seam)模式

一个可换能力拆成三个角色:**Service Definition**(声明接口)、**Service Provider**(实现,常为插件)、**Consumer**(消费方,常为模型工具)。三个角色都在才算一个缝;只实现一个角色不算。

收益:换一个 provider 就换整个产品行为。例如 fs 与 subprocess 共享"同一执行世界",挂上 `fs-e2b`+`subprocess-e2b` 两个适配器,Bash/PTY/LSP 整体迁入远程沙箱,消费方零改动。

## 8. 事件域划分(选事件域是改代码的第一决策)

- **session 事件** = 耐久事实(可重放,模型可见);
- **agent 事件** = 在途控制(inbox、status、error、pre-step/request 瀑布);
- **capability 事件** = 接缝策略(`fs/*`、`tools/*`、`telemetry/*`),不 import 循环即可挂。

## 9. 扩展速查(官方"新行为放哪"表节选)

| 目标 | 机制 |
|---|---|
| 加模型提供商 | `ctx.llm.registerAdapter([...], adapter)` |
| 加模型工具 | `ctx.tools.register()`(schema 自动进提示词组装) |
| 某会话不同能力集 | 组合 agent preset,service 行用 `isolate` realm |
| 加 shell 执行 | 注册 `ctx.shell` 后端(本地经 `ctx.subprocess` spawn) |
| 加持久终端 | `ctx.terminals` 后端 + `dsh-tool-terminal` |
| 加后台任务 | `ctx.jobs` + `job_*` 工具 |
| 拦截请求/工具/turn | `agent/*` 或 `tools/*` 事件;`agent/turn-stopping` 停 turn |
| 注入模型上下文 | `agent.inject()` → 落到下一个被接纳的请求 |
| 加 UI | 驱动 `ctx.agents`,渲染 `session/event` |
| 加持久会话状态 | 扩展 `SessionEventMap`,从日志渲染与重放 |
| fork 会话 | `ctx.sessions.fork(source, boundary?, childId?)` |
| 注册仅限某 agent | 用该 agent 的 `agent.ctx` 注册 |

## 10. 工程与质量观察

- 双聚合 TS 工程(Host/Client 分开),`Context` 接口两侧 declaration merge 同 key 不同服务,合在一个 program 会冲突——这是构建布局的根因。
- 文档即契约:子系统文档用 ` ```ts type-equiv ` 贴源码等价声明,`verify-type-equiv` 门禁防漂移;每页有中英双语对。
- 大量 invariant 伴生包(`src/invariant.ts`):关键不变量(如"模型可见即已记录"、turn/step 配对)有运行时校验。
- 设计强一致性:事件+fold、瀑布+守卫、可逆 effect、fail-closed 安全默认,处处可见。
