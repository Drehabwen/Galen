## 1. 产品定位

Galen 是面向医学科研团队的 **对话驱动科研协作工作站**。

它不是医学版 Word，不是普通 AI Chat，也不是面向程序员的 IDE。Galen 的核心是把医生或研究者在对话中表达的科研意图，转化为可确认的研究计划、可拆分的执行 Session、可复现的代码运行过程、可追踪的证据链和可交付的科研产物。

核心链路：

> 对话确认计划，计划生成画布，画布拆分 Session，Session 执行代码，结果回流主线程。

更完整地说：

> 主线程负责目标与关键决策，计划画布负责任务编排，独立 Session 负责执行与上下文隔离，代码负责可复现科研过程，证据链负责可信度，文档与产物负责最终交付。

## 2. 核心判断

上一版 Galen 容易落入三个并列中心：

- Chat 是一个中心。
- Code 是一个中心。
- Document 是一个中心。

这会导致界面没有重心，也会让产品退化为“AI 聊天 + 文档编辑 + 代码面板”的拼装形态。

v0.2 必须重新定义主次：

- **主驾驶是主线程对话**：用户在这里提出目标、确认假设、修改计划、接收回流结果。
- **主工作区是计划画布**：确认后的研究计划在这里变成节点化、可执行、可分派的科研流程。
- **执行单元是独立 Session**：每个节点拥有独立上下文、代码、日志、输入、输出、证据和负责人。
- **代码是执行层，不是默认主界面**：代码可以进入 Session 后查看和运行，但不应默认抢占医生的主视线。
- **文档是产物层，不是第一交互中心**：方法学、结果、图表、论文段落由 Session 结果回流生成。

## 3. 目标用户

### 3.1 主要用户

- 有真实医学科研任务的临床医生。
- 需要将科研问题推进到方案、数据、统计和论文的 PI 或课题负责人。
- 医学研究生、规培医生、住院医师。
- 科研助理、数据整理人员、文献整理人员。

### 3.2 协作用户

- 统计师。
- 数据工程或数据治理人员。
- 导师、共同作者、通讯作者。
- 科研管理、伦理、数据质量或方法学审查人员。

## 4. 用户问题

医学科研协作当前的问题不是单点工具不足，而是科研过程被割裂在多个上下文中：

- 科研目标在聊天工具里，执行计划在文档里，代码在脚本里，证据在 PDF 或网页里。
- 一个大聊天窗口会不断吞入代码、日志、文献、表格和讨论记录，最终上下文爆炸。
- 每个任务的输入、输出、负责人和执行状态不清晰。
- 研究者难以判断 AI 已经做了什么、基于什么证据、产物是否可复现。
- 协作者只能接收模糊任务，缺乏明确节点、上下文、交付物和确认状态。

Galen v0.2 要解决的是：

> 让科研工作从“无限聊天和散落文件”变成“主线程决策 + 计划画布编排 + 独立 Session 执行 + 结构化结果回流”。

## 5. 产品原则

### 5.1 对话驱动计划

用户不直接创建复杂任务图，而是在主线程中用自然语言描述科研目标、数据范围、研究对象、主要结局和统计偏好。

Galen 在主线程中生成计划草案，并要求用户确认关键假设：

- 研究类型。
- 数据范围。
- 研究对象。
- 纳入排除标准。
- 暴露分组。
- 主要结局和次要结局。
- 统计方法。
- 证据来源。

只有计划确认后，右侧计划画布才正式生成 Session 节点。

### 5.2 计划生成画布

计划画布不是手动画流程图工具，而是被主线程确认后的科研执行结构。

画布承载：

- Session 节点。
- 节点之间的输入输出关系。
- 并行与串行关系。
- 结果回流关系。
- 节点状态。
- 负责人。
- 待确认风险。

画布应具有“空画布 + 节点链接”的感觉，但要避免变成玩具化思维导图。它必须服务于医学科研执行。

### 5.3 Session 隔离上下文

每个 Session 是一个独立执行单元，拥有自己的上下文边界。

Session 内可以包含：

- 任务目标。
- 输入材料。
- 代码和工具调用。
- 日志。
- 证据。
- 中间文件。
- 产物。
- 风险提示。
- 人工确认记录。

主线程不直接吞入 Session 的完整上下文，只接收结构化回流结果。

这样可以避免上下文爆炸，并让科研流程更可审计。

### 5.4 代码驱动执行

Galen 的可复现能力来自代码执行。

代码用于：

- 队列定义。
- 数据清洗。
- 变量字典校验。
- 统计分析。
- 表格生成。
- 图表生成。
- 文档片段生成。
- 结果校验。

但是代码默认藏在 Session 内部。医生可以选择进入 Session 查看，也可以批准放行，让 Galen 自动执行。

### 5.5 结果回流主线程

Session 完成后，不能把完整聊天、日志、代码全部塞回主线程。

回流内容应是结构化摘要：

- 执行了什么。
- 使用了哪些输入。
- 生成了哪些产物。
- 关键结果是什么。
- 代码版本是什么。
- 证据依据是什么。
- 有哪些风险或待确认项。
- 是否建议进入下一节点。

主线程保留决策历史和关键结果，而不是承载所有原始上下文。

### 5.6 节点可进入、可放行、可分派

每个 Session 节点至少支持三类操作：

- **进入 Session**：查看详细上下文、代码、日志、证据和产物。
- **批准放行**：用户确认后允许 AI 执行该节点。
- **分派他人**：将节点交给统计师、研究生、共同作者或其他协作者。

这使 Galen 从个人 AI 工具升级为科研协作系统。

## 6. 核心体验模型

### 6.1 计划确认前

界面采用左右并行结构：

- 左侧是主线程对话区。
- 右侧是待生成的科研计划画布。

此时主线程是绝对主角。

用户与 Galen 讨论研究目标，Galen 逐步提出计划草案。右侧可以展示轻量的“计划预览”或空画布状态，但不能提前展示完整执行画布。

关键动作：

- 生成计划草案。
- 修改计划草案。
- 确认关键假设。
- 点击 `确认计划`。

### 6.2 计划确认后

确认后，右侧生成科研计划画布。

布局变为：

- 左侧：主线程，继续承载决策、确认和结果回流。
- 右侧：科研计划画布，承载 Session 节点和执行状态。
- 画布内抽屉：展示当前选中 Session 的详情。

此时主线程仍然是驱动入口，画布成为执行编排区。

### 6.3 Session 执行中

用户可以选择：

- 不进入 Session，直接批准自动执行。
- 进入 Session 查看代码、日志、证据和产物。
- 分派给协作者。

Session 执行结束后，将结构化结果回流主线程，并更新画布节点状态。

### 6.4 结果产出

多个 Session 完成后，Galen 可生成：

- 队列定义表。
- 纳排流程图。
- 数据清洗报告。
- Table 1 基线特征表。
- 统计模型结果。
- Figure 图表。
- 方法学段落。
- 结果段落。
- 论文草稿。
- 报告或投稿包。

产物必须能追溯到对应 Session、代码、证据和确认记录。

2. 左侧项目栏。

内容：

- `对话驱动科研协作`
- 工作区选择：`医学科研`
- AI 状态：`AI 规划中` / `AI 执行中` / `等待确认`

### 7.3 左侧项目栏

内容：

- `我的课题`
- 搜索。
- 课题列表。
- 当前课题状态。
- 工作区选择。
- 设置。

项目状态示例：

- `计划编排中`
- `计划已确认`
- `Session 运行中`
- `等待确认`
- `已归档`

### 7.4 主线程

主线程不是普通聊天窗口，而是科研决策和结果回流的主时间线。

必须支持：

- 用户提出科研目标。
- Galen 生成计划草案。
- Galen 请求确认关键假设。
- 用户确认或调整计划。
- Session 结果回流。
- 待确认卡片。
- 风险提示。
- 继续追问和调整计划。

主线程内的关键卡片：

- `计划草案`
- `待确认假设`
- `Session 回流结果`
- `风险提示`
- `产物生成`
- `下一步建议`

### 7.5 科研计划画布

画布用于展示计划确认后生成的 Session 流程。

画布节点示例：

- `01 课题定义`
- `02 文献证据`
- `03 队列构建`
- `04 数据清洗`
- `05 统计分析`
- `06 图表与论文`

节点状态：

- `已确认`
- `运行中`
- `待批准`
- `待执行`
- `已完成`
- `已阻塞`
- `已分派`

连线语义：

- `结构化输入`
- `证据摘要`
- `分析数据集`
- `统计结果`
- `结果回流`

详情抽屉展示：

- 独立 Session 标识。
- 目标。

## 10. 关键用户流程

### 10.1 新建研究计划

1. 用户在主线程输入研究目标。
2. Galen 追问缺失信息。
3. Galen 生成计划草案。
4. 用户确认关键假设。
5. 用户点击 `确认计划`。
6. 右侧生成科研计划画布。

### 10.2 批准 Session 执行

1. 用户在画布选择一个待批准节点。
2. 右侧抽屉展示目标、输入、将执行内容和风险。
3. 用户点击 `批准放行`。
4. Session 独立执行。
5. 节点状态更新为 `运行中`。
6. 完成后回流结构化结果到主线程。

### 10.3 进入 Session 深挖

1. 用户点击 `进入 Session`。
2. 打开 Session 详情页。
3. 用户查看代码、日志、证据、产物。
4. 用户可要求修改代码或重新运行。
5. 修改后的结果回流主线程。

### 10.4 分派节点给协作者

1. 用户选择待执行节点。
2. 点击 `分派他人`。
3. 选择统计师、研究生或共同作者。
4. Galen 生成任务说明和交付要求。
5. 协作者在自己的 Session 中处理任务。
6. 结果回流到主线程和画布节点。

### 10.5 结果回流与文档生成

1. 多个 Session 完成。
2. Galen 汇总结构化结果。
3. 用户在主线程确认关键结果。
4. Galen 生成表格、图表、方法学和结果段落。
5. 产物进入产物库，并关联代码、证据和版本。

## 11. 视觉与交互要求

### 11.1 布局

默认桌面布局：

- 左侧项目栏：窄、安静、低权重。
- 中左主线程：约 35% 到 40% 宽度。
- 中右计划画布：约 60% 到 65% 宽度。
- Session 详情作为画布内抽屉，不形成第三个等权主列。

### 11.2 主次

- 主线程是驱动入口。
- 画布是计划确认后的执行空间。
- Session 抽屉是当前节点的上下文。
- 代码、日志、证据和产物默认折叠或在 Session 内查看。

### 11.3 语言

使用正式医学科研语言。

推荐术语：

- `主线程`
- `科研计划画布`
- `独立 Session`
- `确认计划`
- `进入 Session`
- `批准放行`
- `分派他人`
- `结果回流主线程`
- `避免上下文爆炸`
- `可复现`
- `证据链`

避免术语：

- 过度拟人化表达。
- 营销化口号。
- 过度工程化术语暴露给医生。

### 11.4 色彩

沿用 Galen 当前 UI 体系：

- 主背景：临床白和极浅灰。
- 品牌色：医疗绿。
- 待确认：琥珀色。
- 证据和文件链接：蓝色。
- 风险：红色。

实现要求：

- 必须通过 `rust/crates/galen/src/styles/tokens.css` 引用 token。
- 不得在组件中硬编码颜色。
- 不使用紫色渐变、深色仪表盘、营销式背景或装饰光斑。

## 12. 状态模型

### 12.1 项目状态

- `drafting_plan`：计划草案中。
- `plan_pending_confirmation`：等待确认计划。
- `plan_confirmed`：计划已确认。
- `sessions_running`：Session 运行中。
- `pending_review`：等待研究者确认。
- `completed`：已完成。
- `archived`：已归档。

### 12.2 Session 状态

- `pending`：待执行。
- `pending_approval`：待批准。
- `approved`：已批准。
- `assigned`：已分派。
- `running`：运行中。
- `blocked`：已阻塞。
- `completed`：已完成。
- `returned`：已回流主线程。

### 12.3 回流状态

- `draft`：回流草案。
- `needs_review`：需要确认。
- `accepted`：已接受。
- `rejected`：已拒绝。
- `superseded`：已被新结果替代。

## 13. 技术实现要求

### 13.1 前端

- React + TypeScript + Vite。
- 保持现有 Tauri 桌面端架构。
- 新增或重构组件时优先复用 `src/components/ui/`。
- 领域对象放入 `src/domain/`。
- 样式引用 `src/styles/tokens.css`。

建议组件：

- `MainThreadPane`
- `PlanDraftCard`
- `ResearchPlanCanvas`
- `SessionNode`
- `SessionEdge`
- `SessionInspectorDrawer`
- `SessionActionBar`
- `StructuredResultCard`
- `GlobalResourceBar`

### 13.2 后端与本地数据

P0 可以使用前端模拟数据，但对象结构应接近后续真实数据。

后续需要：

- 保存 Research Project。
- 保存 Main Thread。
- 保存 Research Plan。
- 保存 Session Node。
- 保存 Session 运行记录。
- 保存 Artifact。
- 保存 Evidence。
- 保存 Approval 和 Assignment。

### 13.3 上下文边界

必须明确区分：

- 主线程上下文。
- 计划画布上下文。
- 每个 Session 的独立上下文。
- 回流到主线程的结构化摘要。

禁止将所有 Session 原始消息、完整日志和完整代码默认灌入主线程。

## 14. 验收标准

### 14.1 UI 验收

- 第一屏能清楚看出左侧是主线程，右侧是计划画布。
- 计划画布必须表现为“计划确认后生成”。
- Session 节点之间有清晰连接和状态。
- 选中节点后能看到 `进入 Session`、`批准放行`、`分派他人`。
- 代码不应成为默认主视觉。
- 文档不应成为默认主视觉。
- 界面保持留白，不应回到全展开控制台。

### 14.2 产品验收

- 用户能从主线程发起研究目标。
- 用户能看到计划草案并确认。
- 确认后能生成多个 Session 节点。
- 用户能理解每个节点的输入、将执行内容和回流产物。
- 用户能选择自动放行、进入查看或分派他人。
- Session 结果能以结构化摘要回流主线程。
- 主线程不承载所有原始执行上下文。

### 14.3 工程验收

- 前端类型检查通过：`cd rust/crates/galen && npx tsc --noEmit`。
- 设计 token 使用一致。
- 新组件边界清晰，可复用。
- Galen 命名统一，不引入 Claw 或其他产品命名。
- 不破坏现有 Galen 基础启动流程。

## 15. 非目标

当前版本不做：

- EMR/EHR 替代。
- 医疗诊断或治疗决策。
- 通用办公套件。
- 通用白板工具。
- 面向程序员的完整 IDE。
- 默认全展开代码、日志、任务图和文档编辑器。
- 将 Fitwork、康复硬件或运动处方闭环并入 Galen 主线。
